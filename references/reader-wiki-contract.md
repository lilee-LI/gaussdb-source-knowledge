# 最终交付是 Wiki，过程文件留在工作区

## 两个目录，两种用途

```text
成果区/
  wiki/                     用户最终阅读、复制、交给Agent的知识库
    README.md               总览、阅读路线、对象入口、版本与覆盖边界
    errors/                 错误码知识
    assertions/             断言知识
    mechanisms/             共享原理；有实际知识复用才拆页
    procedures/             场景诊断与条件处理
    references/             可读源码依据、版本范围和必要短片段
  .work/                    过程资料，不作为最终知识库交付
    task.json
    product-profile.json
    evidence-store/
    run/                    研究、JSON、原生vault、暂存、回执、检查报告
```

不在最终wiki创建空目录。只交付有内容的Markdown和确有必要的图。当前交付器只发布Markdown。不能把run改名为wiki、打包整个vault或复制一堆研究报告作为完成。工作区保留以支持增量维护和追证据，默认不删除；它不是用户阅读的前置条件。

## 错误码文章要学到什么程度

主文首先讲错误和术语，随后给原因导航、场景和处理；实现细节放后部，不能因“源码置后”就删掉实现。读者按需深入，仍在这套Wiki内获得下列信息。

1. **真实身份与入口**：原消息、错误级别、产品号和SQLSTATE分别是什么；映射差异是什么。列实际调用链，函数名和仓库相对路径必须来自阅读。不同入口分开，未知部分标缺口。
2. **正常机制**：关键对象和字段由谁初始化、什么时候改变、谁消费、为什么保留。不能只写“重新检查失败”。说明执行顺序和关键状态迁移。
3. **失败条件**：把完整谓词、短路、前置护栏和异常发生时点解释清楚。选择真正控制行为的短源码片段，通常数行到十几行；更长则按语义拆解。原样片段与省略/伪代码分开标记。每段有函数、路径、精确revision、行号，并解释“证明什么、不证明什么”。
4. **多条根因链**：对每条有源码支持的成因，写“业务前提→具体生产者/状态变化→检测点的输入如何变化→为什么到达本错误”，以及最近竞争解释。变量比较器不是上游生产者，字段被比较不等于修改基表对应属性就能触发。不要凑数量。
5. **场景与措施相接**：各场景写出能区分原因的材料、支持/排除/未知、适用措施和不适用出口。措施要解释切断哪一步、操作对象、事务/数据意义、回退及后续复验设计；不以重启/重试/调参作为无条件结论。
6. **静态案例与反例**：必要时提供完整可理解的SQL文本/时序示意，仅作源码推导，明确not_run；不伪造运行输出。配最近正常反例，以及错误措施为什么无效。
7. **版本与跨域**：源码/构建宏、集中和分布、角色/连接来源、兼容、内存/等待/系统视图/工具/事务等对本问题的具体影响要可读。不可构建、未知和已读条件分开。不让一张“八域已检查”表代替具体结论。

断言还必须解释实际宏定义/覆盖/极性/求值、合法不变量、写者/别名/所有权/并发、失败动作、未启用后的行为。没有实际破坏者时明确是假设，仍充分讲清已能证明的源码机制，不能只剩“需要更多信息”。

## 源码怎样呈现

- **主文**负责机制与各根因的完整解释，不能只放三行摘要和链接。
- **共享机制页**负责被多对象复用的详细原理；主文仍保留必要摘要，避免无止境跳页。
- **源码依据页**按知识问题组织短片段和精确位置，不按文件顺序倾倒源码。每个片段只存一次，多处引用普通Markdown锚点。
- 全文件/大窗口、完整检索日志、哈希账和机器证据只留.work。不从文章链接到JSON、私有research或_raw。源码依据页须在没有证据仓时也能解释关键检查；授权环境可继续回到绑定源码核对全上下文。
- 不用固定字数、片段数或页数代替学习质量。短错误也要讲清生产者和边界，复杂错误按独立机制展开。

## 读者验收，而非文件数量验收

Agent关闭研究报告和JSON，只从候选Wiki回答：错误是什么意思？对象正常如何工作？哪些不同路径能触发？我需要什么材料区分？每种情况怎样有条件处理，什么做法无效？哪段源码支持结论？换构建/版本时什么不能沿用？

把具体发现记在工作区integration.json的reader_review，不只填“已检查”。记录mode、findings（identity/normal_path/failure_predicate/cause_branches/scenario_remedies/counterexamples/source_explanation/scope）、readback_answer及page_hashes。哈希只能绑定审阅文本，不证明读懂源码；语义仍由实际阅读负责。正文缺源码解释、把多个原因压成同义句、只给“查看日志/重建缓存”、要求查JSON才能理解时，退回补学和重写。

使用`standard=source-wiki-reader/v1`，八项`section_refs`分别指向本轮Wiki实际交付页及其章节锚点；不能用示范页代替新产品研究。迁移时按质量保持要求（旧版资料）先读完整成品示范，再做目标源码研究和回读。交付器核章节存在和当前正文绑定，语义深度仍须逐条复核。

所有文章经实际Wiki Skills维护和check后，写工作区run/WIKI-README.md，再执行：

```text
python -X utf8 scripts/source_wiki.py deliver --run 成果区/.work/run --output 成果区/wiki
```

deliver重做原流程检查，核读者审阅绑定，只复制声明过的知识Markdown，去掉私有快照/关系/置信度管理属性，检查全库相对链接和标题锚点，最后生成独立wiki。遇到断链、JSON链接或未审阅新正文时拒绝交付；不自动删掉证据链接蒙混通过。不覆盖已有wiki，更新时选新交付目录并保留旧版。

交付报告、JSON和执行记录只写.work。最终答复只给wiki/README.md、核心页入口、实际改进与尚未覆盖范围。不要用“工具全部通过”代替具体知识质量说明。
