# 逻辑解码：事务、快照、位点、资源保留与重启

与 [公共深度规则](../common/research-depth.md) 一起使用。逻辑解码链横跨 WAL、事务、catalog 可见性、重排、插件、传输、确认和持久化；看到一个 LSN 赋值不能解释端到端投递语义。

## 先划定层次

声明 SQL/复制协议/内部调用入口，slot 类型和数据库归属、插件/输出格式、源端构建、消费者及其确认策略。物理复制、逻辑 WAL 读取、插件生成记录、网络发送、客户端接收、下游事务提交分别建层。

“已消费”必须标明是哪层的动作。消费者报告某个位点，不自动等于下游业务事务持久化；服务器保存确认，也不自动证明恢复后不会重复。端到端 exactly-once 需要消费端事务/幂等与确认协议证据，本领域源码只能证明其中一段。

## 追到完整事务和快照链

| 子链 | 核心调查 |
|---|---|
| slot 生命周期 | 创建、获取/释放、并发占用、数据库限制、持久/临时、保存/恢复、删除 |
| WAL 读取 | 起始位置选择、record reader、跨段/缺段、重试/等待、解码分派 |
| 快照构造 | 初始状态、达到一致点的条件、事务可见性、catalog xmin、导出/恢复 |
| 重排 | xid/subxid、change 归属、提交/回滚、提交顺序、spill/恢复/清理 |
| 插件 | 装载、startup、begin/change/commit 等回调、过滤、输出资源与错误 |
| 发送与反馈 | 输出缓冲、发送进度、客户端反馈来源、校验、推进与持久化时机 |
| 异常与重启 | 停止点、保存状态、重新读取区间、重复/遗漏风险、清理和再次可达 |

状态机要列初始化、转移条件、正常终点和异常出口。遇到函数回调或封装继续追当前插件和调用契约；通用框架支持回调，不等于任意插件具有相同过滤/格式/事务保证。

事务研究至少覆盖正常提交、回滚和与任务有关的子事务/长事务；两阶段、并行、流式大事务等先确认该版本是否实现并如何启用，不能沿用上游其他版本能力。

## 给每种位点建立账本

不能只画一个“消费进度”。对实际存在的字段逐个记录：类型/单位、生产者、推进条件、锁和并发、内存值/持久值、下游用途、重启读取者、可见接口。

| 常见研究对象 | 必须区分的问题 |
|---|---|
| 请求起点/读取位置 | 调用者请求、内部修正、实际从哪段 WAL 开始读 |
| restart_lsn 一类保留位置 | 为什么还需要更旧 WAL、何时能推进、持久化与回收关系 |
| confirmed_flush 一类确认位置 | 来自何种反馈/调用、校验范围、何时保存、能证明哪个层次 |
| catalog_xmin/xmin | 哪种可见性受保护、由谁更新、何时释放、对回收的影响 |
| 发送/输出位置 | 生成、发送、接收和下游持久化是否是同一事件 |

这些名称仅作常见入口，精确语义以当前提交为准。某字段没有发现时记为未映射，不编造。不能把 LSN 的差值直接称为业务记录数、时间延迟或消费者已提交量。

## 资源保留与故障解释

分别研究 WAL 保留、catalog/行版本保留、重排内存、spill 文件和输出缓冲。长事务可能让“已发送进度很新但旧资源仍保留”成立，具体要找推进约束，而不是笼统归因为消费慢。

对内存增长加载 memory，追上下文所有者、事务结束清理、spill 阈值和恢复路径；对读/写阻塞加载 waits；对 slot 视图加载 views，核对字段是否实时、权限及空值。磁盘不足、WAL 不可用、插件失败和权限错误要回到各检测点，不能统一建议重建 slot。

删除/重建 slot 可能改变一致点和可恢复区间；提出措施前先说明未消费数据如何处理、能否重新建立一致基线、消费者如何防止重复或遗漏。不能用“释放空间”掩盖数据链变化。

## 可执行的验证矩阵

隔离环境先建立小事务基线，再按问题选择：提交/回滚、长事务夹杂短事务、子事务、积压、受控中断、服务端/消费者重启、插件报错。每例保存源端事务身份/提交顺序、WAL/slot 位点时间线、插件输出、消费者确认和下游持久化结果。

先从源码生成各层预期，再比较实测；只做创建上下文的静态分析，不能宣称全链路重启验证完成。无法控制消费者时，准确保留确认到持久化之间的未知段。

## 交付与充分性

`transaction_and_snapshot` 写事务可见性/重排/插件流水线；`positions_and_confirmation` 写逐位点账本和确认层次；`resources_and_restart` 写资源保留、异常清理和重启验证边界。

复核用“读取起点与允许输出起点不同”“确认已推进但资源未释放”“下游已收但尚未提交”中相关案例挑战解释。未追反馈写入者、保存恢复或消费者事务时，就不能给出超出已读链条的投递保证。
