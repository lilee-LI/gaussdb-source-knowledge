# 错误学习的跨领域、构建与节点适用性

本规程是完整错误码学习的必读、必交付项。它与因果研究和源码闭合账共同使用。所有结论均为纯源码研究；不连接实例、不执行 SQL、编译、configure/CMake 或代码生成器。可读取已有受控构建配置、生成头和编译命令清单；没有这些材料时分别研究有依据的条件分支。

## 1. 先建立产品与构建边界

分别记录源码身份、构建能力、运行角色、连接来源、运行配置和数据表示，不能把它们合并为一个“版本”。每次检查集中式、分布式两个产品形态：已支持、有依据不适用、构建入口明确拒绝、缺少源码、尚未知。这里只要求实际判定，不要求不存在的产品路径也能研究完成。

构建事实从配置入口到实际使用点核对：

1. CMake/Make/configure/产品脚本如何选文件、库、生成实现和替代实现。
2. 选项怎样形成 `-D`、`-U`、生成头或头文件定义；读取默认值之后，还要查强制赋值和覆盖顺序。
3. 宏在什么编译单元有效，是否有嵌套条件、include 顺序或文件内重定义。`#ifdef X` 与 `#if X` 不等价：定义为 0 仍满足前者。
4. 角色判断宏最终读哪个状态；该状态由谁初始化、在哪些入口改变；连接来源与执行线程性质是否影响判断。
5. 会话/启动参数在哪里读取、何时生效；缓存创建时保存的值不能由事后当前配置替代。
6. 涉及尺寸计算时绑定类型宽度、符号性、对齐和数据布局。未确认 ABI 的数字只能作为有前提的算术推导。

宏名和函数名不是语义证据。公开源码中的 `PGXC`、`IS_PGXC_DATANODE` 只是应当追定义的示例，不能作为所有产品的固定判定规则。内部 GaussDB 的宏名、生成逻辑与节点模型需要重新发现。

研究的最小适用单元是一个 **variant（条件组合）**。每个组合写清构建入口、宏谓词、运行角色/连接来源、配置与 ABI 前提、所需证据、未知及限制。未知目标构建与未读源码是两件事：静态机制可在明确条件下成立；实际部署是否符合条件仍未知。

## 2. 证明整条路径在同一组合下成立

对每个检测点、成因、采集项和措施建立适用关系。依次证明：文件参与构建 → 编译条件成立 → 实际实现/方法表被选择 → 角色与入口匹配 → 状态和前置护栏允许 → 到达检测或动作。

同一条因果链的入口、状态写者、检测点和清理必须使用相同条件组合。不可将集中式入口、分布式状态生产者和另一种分配器的清理拼成一条路径。动态分派、插件、缓存、专用存储引擎和生成实现按相关性追踪到真实选择点。

必需展示“适用变体表”和“分支覆盖表”。可达、已证明不可达、未分析、源码缺失分别表达；在一个构建下关闭的分支仍保留为其他组合的候选。目标 profile 未绑定时不能把 unknown 当作 disabled。

只展开会改变错误含义、可达性、判别、观测范围或恢复语义的组合。可合并行为等价的组合，但记录等价范围、理由及证据；不能仅因文章太长合并。每个相关维度至少给一个分支差异或不影响该结论的证据，不机械枚举全量笛卡尔积。

## 3. 跨领域以具体问题交接

每次必检八项：兼容性 `compatibility`、等待事件与耗时分析 `waits`、系统视图 `views`、内存 `memory`、工具 `tools`、逻辑解码 `decoding`、事务并发 `transactions`、对象与权限 `objects`。逐项登记 required / not_involved / unknown；不涉及必须有范围及依据，缺少实现属于 unknown，不能填写 not_involved。

每条依赖区分四种关系：

| 关系 | 要交付的答案 |
|---|---|
| causal 成因 | 谁生产失败输入/状态，经过哪些转换，由哪个检测点消费 |
| observation 观测 | 视图/日志的字段生产者、节点/会话/权限、时点与重置；无行/NULL/失败可说明什么 |
| recovery 恢复 | 事务、锁、内存、位点及外部副作用决定哪些动作可行，哪些必须退出 |
| applicability 适用性 | 构建、角色、模式或入口决定以上关系何时存在 |

交接包括问题、发起的点/原因/场景、variant、生产者→变换→消费者、真实证据、结论/缺口、影响的判别和措施、变化时须重审的源码。主错误 Skill 整合答案；必要时在当前任务定向研究，或使用同产品、版本和条件下重新核验的机制页。无需为一个子问题加载整个领域，也无需外部 Skill 才能完成迁移包的工作。

共享机制只维护一份有条件的事实。Wiki 关系应表达“导致、观测、约束恢复、条件适用”，不能仅列相关链接。机制变更时沿依赖找回原因、场景和措施；源码文案未变不代表机制未变。

## 4. 错误传播和恢复必须成链

每个相关组合都说明：原始失败节点/线程/阶段 → 错误构造 → 捕获/包装/转发 → 客户端可见字段 → 取消/回滚 → 资源与远端状态清理 → 重试或其他动作边界。

集中式也检查进程/线程、连接与异步边界。分布式特别追：首发错误与展示错误是否同源，节点错误如何选择或合并，其他节点已发生哪些效果，取消与回滚传播到哪里，失败后哪些缓存/锁/连接仍存活。不能由本地 ERROR 推导全节点原子回滚，不能由本地对象删除推导远端同名对象同步删除。

采集和措施都要绑定节点、物理连接、对象所有者、时间范围。某个节点视图无行，不足以证明其他节点没有相应状态。SQL 会话中的对象不能由另一个诊断连接的同名对象替代。数据库未包含的客户端/运维系统源码可列现场前提；已经纳入研究范围却缺失的源码则列研究缺口。

## 5. 交付、反例与拒绝条件

新增必交付：构建/角色变体表、逐项分支覆盖、八领域依赖及影响、传播与恢复链、适用性反例、逐条结论与变体的映射。可读文章保留摘要，详细证据放研究记录。默认另存 `applicability.json`，便于执行结构检查和跨环境移植；不用 Python 时仍必须按同样字段人工审阅。

反例至少挑战本次相关条件：同源码更换宏/角色/参数后原链是否失效；更早护栏是否先报另一错误；错误从远端转来时采集与处理是否作用于错误对象。不能声称每次必须有真实可用的两种产品，缺失条件明确列出。

必要依赖或传播步骤开放时，依赖它的就绪措施不得发布；已有证据的局部机制仍可条件化交付。不可构建组合不能宣称为实际支持的产品。完整状态仅表示声明范围内已闭合，不能通过无依据排除分布式/共享路径获得。

机器检查只核对声明、关联、状态和证据引用。它不求解完整 C/C++ 预处理器，不证明没有漏分支，也不认证实际二进制。审阅者须阅读关键定义与反例，检查是否把必要分支塞入范围外。研究与文章都标明 source_only、not_run、not_assessed；自查与独立审阅如实分开。

## 6. 适用性账字段与使用

| 字段 | 填写方式 |
|---|---|
| source_binding | product、revision、binding_id；独立包与产品档案一致，主工程 binding_id 使用任务 snapshot_id |
| subjects | 报错点 site、成因 cause、采集 collection、措施 action 的稳定 ID；depends_on 绑定上游 ID，不得悬挂或成环 |
| variants | 每个相关组合一行；form 为 centralized/distributed/unknown，build_status 为 supported/infeasible/unknown，target_status 为 conditional/confirmed；两个产品形态都必须有判定 |
| macros / runtime_settings | 宏定义状态和值、来源、覆盖顺序、作用范围、E-ID；运行参数另记作用域与读取阶段 |
| dependencies | 八域的具体问题、四种关系、涉及对象与组合、必要性/状态、源码结论、E-ID和下一步；缺证据不等于不涉及 |
| applications | 每个 subject×variant 一行 read/open/infeasible；必须列其全部适用 DEP-ID。研究只建必要的组合，不枚举所有开关 |
| propagation | 每个 variant 的首发/报告/观察/清理/恢复所有者、消息链和清理链；read 需两条真实证据链，不能只列函数名 |
| counterexamples / equivalences | 换条件后路径差异；每个组合要被反例审查覆盖。等价可空，合并只能针对分别已读的成员路径 |
| conclusion | partial 或 complete_within_scope，以及声明范围和理由 |

subjects 中 supported/open 用于点和成因，ready/withheld 用于采集与措施；具体可用范围由 applications 决定。ready 对象仅在自身和上游均 read、必要依赖闭合、传播恢复已读的组合中可条件使用。其他组合仍可 open，不能把局部就绪扩大为全产品就绪。

模板是未填写骨架，不能通过验收。先建立 subjects、variants、dependencies，再生成逐对象适用行并逐条审阅；不要用自动填 read/closed 代替源码研究。检查通过后仍须读者审阅，包括正文、表与账是否一致。
