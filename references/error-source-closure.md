# 错误源码学习的范围与闭合账

本规程用于完整的新错误码学习。任务同时设置 `execution_profile=source_only`、`analysis_contract=error-causal/v1`、`source_closure_required=true`。研究仍使用 `error-causal/v1`，增加 `source_closure`；历史任务不因工具更新被要求补字段，也不会自动升级质量声明。

目标是回答两个独立问题：**在什么源码范围找过哪些候选？支持结论所需的因果段是否已经读完？** 已声明的报错点全部有解释，并不能说明漏搜的点不存在；有一条正确局部机制，也不能说明现场处理规程已经具备充分前提。

## 一、先声明可复核的搜索边界

记录产品、源码版本/快照、可访问目录、实际入口、编译分支、已获得与缺少的生成文件。`scope` 写本轮包括什么；`search_limitations` 写搜索工具、动态字符串、宏展开、未获得目录、第三方组件等限制。结论只对该边界成立，不因源码相似而从 openGauss 外推到 GaussDB。

沿编号、主消息固定片段、SQLSTATE、包装宏和调用者检索；这些轴可以得到空结果，但必须保留实际查询及解释。SQLSTATE 未找到、未设置或不适用时，`identity.sqlstates=[]`，由 `mapping_limitations` 说明是哪一种情况和所依据范围。禁止为满足模板捏造一个状态码。GAUSS 编号绑定与 SQLSTATE 绑定要分别说明。

每个实际候选在 `candidates` 有一行：

| 字段 | 内容 |
|---|---|
| id / location | 本轮稳定候选 ID；具体文件、函数、生成目录项或尚缺的源码位置 |
| search_axes | 通过哪些真实搜索轴发现 |
| disposition | included：纳入检测点；excluded：有依据排除；unresolved：尚无法判定 |
| site_ids | included 必须绑定检测点；其他状态保留空集合 |
| reason / evidence_ids | 纳入或排除的理由与真实证据；未决候选可没有源码证据 |
| next_step | 未决项下一步需要读哪个定义、目录或版本材料 |

所有声明检测点必须能返回至少一个 included 候选。注释、翻译重复、测试夹具、关闭的构建分支、不同版本映射不能无说明地消失；记录为 excluded 或 unresolved。搜索无命中也不能伪造候选，应在原检索表和限制中解释。

## 二、把“还要读什么”写成证明义务

`obligations` 是尚待阅读或已闭合的具体问题，不是再抄一遍五项清单。每个检测点和成因至少实际考察以下轴：

| kind | 要闭合的问题 |
|---|---|
| entry | 实际 SQL/工具入口、解析与重载绑定、调用者；哪些入口被排除，排除依据是什么 |
| state_writer | 失败谓词的操作数从何形成；初始化、修改者、生命周期、数据流及并发保护；缺少写者时保留开放 |
| guard | 前置检查、短路顺序、兼容与配置、宏和编译分支是否让路径可达，是否先触发另一个错误 |
| cleanup | 失败前副作用、异常传播、事务和连接状态、资源所有权与清理；这决定是否可以安全修复或重试 |
| domain | 哪个相关领域问题影响本结论；与共用 `source_analysis.domain_dependencies` 对齐 |

同一轴可有多个义务。一个 `state_writer` 行不能用“已追踪”概括未读过的多条写入路径。适用的状态写者、入口或包装层新增后，要增加相应问题，再检查既有原因和措施是否仍成立。

源码闭合与现场确认分开：数据库源码内的输入转换、状态写入者和调用路径是研究义务；未纳入研究范围的客户应用代码、历史输入、当时配置等属于现场确认材料，不得仅因这些材料缺失而把源码义务标 open，或要求连接实例才能完成。只有明确纳入的应用/驱动/工具源码缺失时，才相应保留源码缺口。现场真实原因始终可为 not_assessed，条件方案仍须写清所需材料和适用前提。

每行包含 `id/kind/question/site_ids/cause_ids/domain/status/conclusion/evidence_ids/next_step`。`cause_ids=[]` 表示这是所列检测点所有成因共同依赖的义务；非空表示只影响列出的原因，并应说明该限制。非 domain 义务的 `domain` 写空字符串。

- `closed`：在声明范围内已给出可追溯答案。不是“工具没有报错”，也不代表已编译或运行。
- `open`：缺源码、尚未读完、存在推理跳跃或并发顺序未能证明。写具体下一步；不能只写“后续验证”。
- `not_applicable`：以实际范围和证据说明为什么不涉及，不能用它代替未知。

每个成因的 `obligation_ids` 必须包含全部适用义务。共用依赖中为 required/unknown 的领域，在对应检测点和原因中都要有 domain 义务；closed 只能对应共用表中 `in_task` 或 `accepted_task` 的已解决必要依赖。共用表开放而本表闭合会被拒绝。

必要领域只研究当前错误所需的问题，不为填表研究整个领域。例如错误取决于某兼容开关，就闭合开关读取层、作用域和两侧路径；不必学习全部兼容性函数。

## 三、区分局部原理成立与方案已经可用

源码能支持“在条件 P 下，函数会进入检测点 E”，即使外部调用者或失败清理还存在缺口。这样的局部机制可以明确范围后保留为 `source_supported`，但不能由此生成完整的客户归因或就绪动作。

只要某场景所用原因仍绑定 open 义务，该场景不能标 `conditional_playbook`。相应检测点不能标 covered。可以写 `source_gap`、`needs_evidence` 或 `no_safe_action`，说明下一步，不必凑处理命令。真正没有安全动作并不妨碍说明已经读清楚的正常与错误机制。

多因场景标为 conditional_playbook 时，每个列出的成因都要有适用措施，并由判别条件决定采用哪项。不能把原因 A/B 放在同一场景中，只提供 A 的处理，却宣称整个场景就绪。措施的前提、权限、业务语义、回退和失败出口仍遵循错误因果规程；这些动作全部是未执行的条件设计。

## 四、停止条件与交付状态

`conclusion.status` 只有两类：

| 状态 | 何时使用 |
|---|---|
| complete_within_scope | 已声明搜索范围内所有候选完成处置，适用证明义务无 open，检测覆盖无 open，反例和语义审阅均完成；理由明确范围 |
| partial | 仍有未决候选、开放义务、未解释检测点，或本轮只能给出有限知识；列明缺口及后续材料 |

工具只能核对账目、引用和显式状态，不能证明没有遗漏的候选、C/C++ 解释一定正确、外部世界全部成因已经穷尽。语义审阅还必须检查：搜索范围是否被不合理缩窄、必要路径是否被塞入 out_of_scope、not_applicable 是否有依据、closed 是否实际上含推理跳跃。

完成不是固定轮数或阅读行数。只有当继续沿当前因果问题追踪不会增加新的适用分支，或新分支已记为开放并缩小结论范围，才停止本轮。源码包缺少模块时可以诚实交付 partial；不能为了得到 complete 而制造上游成因、现场数据或解决方案。

## 五、验收与版本维护

报告分别给出候选 included/excluded/unresolved 数、义务 closed/open/not_applicable 数、实际源码范围、机制与方案状态、真实审阅方式。源码 case 仍为 not_run，数据库执行数为零。合成工具测试验证契约行为；真实 openGauss 源码演练验证方法可操作性，两者都不等于 GaussDB 产品结论。

迁入内部环境后，重新绑定内部源码、编号生成逻辑、编译分支和产品边界，再建立新的候选与义务账。公开项目的状态、引用、哈希与“已完成”结论不作为内部版本已学习的凭证。源码变更影响检测点、操作数写者、护栏、清理或相关领域时，通过义务引用定位受影响的原因、场景与措施，形成新任务或修订。

本扩展契约位于 [error-source-closure-v1.schema.json](../contracts/error-source-closure-v1.schema.json)。新任务方法冻结必须同时保存本规程、此契约和使用的 `error-causal/v1` 方法；历史冻结文件不追写。
