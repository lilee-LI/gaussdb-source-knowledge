# 错误知识的读者阅读顺序

面向第一次看到该报错的数据库使用者和支持人员。源码研究可以复杂，文章入口必须可读：不能要求读者先理解 SQLSTATE、事务隔离缩写或内核函数，才能知道发生了什么。本文适用于 errors，以及与错误主题关联的 scenarios、mechanisms 和 procedures。

## 先让读者看懂错误

1. 一句话说出发生了什么，再给一个贴近业务的简短例子。例子须符合已有来源，不将合成场景写成客户事实；大尺寸、破坏性或并发失败实验不要放在入门示例中诱导直接执行。
2. 明确区分 GAUSS 产品/手册编号、五位 SQLSTATE 和消息正文。解释每个列出的码的中文含义、来源及适用范围。仅作为检索别名的 GAUSS 编号不能写成目标构建实际返回；SQLSTATE 相同也不能推断是同一个检测点。
3. 写“先把术语讲清楚”：首次出现的重要英文、缩写、配置项和内部参数要说明中文含义、在本问题中的作用和必要边界。不要用另一个未解释缩写解释它。读者应能回答：对象是什么、何时起作用、为什么影响本次报错。
4. 然后讲可能原因和区分信息、按原因选择的处理步骤、影响与失败出口、怎样确认业务恢复。详细采集 SQL 可以独立成节，解释每项结果会改变哪个判断；不能让字段清单代替诊断。
5. 深入实现、文件/函数/行号、提交哈希、来源绑定和研究台账放在文末。前部只保留影响使用决策的产品版本与实验范围。将原始源码引用移到文末时，保留“支撑哪一条说明 → 原始源码定位/来源记录”的对应关系，不能变成无上下文的文件列表。

推荐阅读顺序：**先看懂这个错误 → 先把术语讲清楚 → 可能原因与判断 → 处理方法 → 采集与恢复验证 → 适用边界、源码依据与实现细节**。机制页可以在术语后解释机制，规程页可以在术语后列实验前提和用例，无需虚构原因或生产处理方案。相关页应能独立阅读，但只解释本页真正需要的术语。

## 粒度示例

不合格：

> 55P03先判断NOWAIT或显式waitSec，识别hold lock和requested waiter。

合格：

> 55P03 是 SQLSTATE，表示这次操作没有取得所需的锁。NOWAIT 表示拿不到锁就立即报错，不继续排队等待；waitSec 是实现中表示本次锁请求等待秒数的参数。具体返回要按语句入口和版本判断。DETAIL 写 hold lock，提供的是一个已持有冲突锁的线索；写 lock requested waiter，提供的是一个排在前面的冲突请求，它自己也可能还没拿到锁。这些字段没有列出所有阻塞者。

其他错误也按同样粒度：40001 先解释并发修改和旧快照，再解释 RR/RC；29P06 先解释结果列结构发生变化，再讲 PREPARE、typmod 和 search_path；22023 的非法分配尺寸先解释“一次申请多大”，再区分单对象上限与实例总内存；22P02 先解释文本不能按 numeric 规则解析，再讲精度、空串、NULL、模式和导入入口。

## 发布前实际复核

沿用户阅读顺序逐页检查，而不是只统计标题：

- 不打开源码，能否解释错误含义、区别近邻错误，并说明为什么选择下一项采集或措施？
- 文中每个会改变处理选择的码、缩写、配置或状态是否先解释了？错误号是否区分手册别名与实测返回？
- “怎么处理”是否包含适用前提、原连接/事务边界、可能影响、失败退出和业务结果复验？
- 移到后面的源码引用是否仍能回到支撑的说明，SQL、事实、反例、版本限制与原始实验是否被保留？
- 是否只改阅读组织，却错误地提升了运行验证、覆盖范围或独立审核状态？
