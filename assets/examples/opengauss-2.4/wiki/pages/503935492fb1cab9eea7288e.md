# geqo_eval 以 GEQO 子内存上下文隔离单次 gimme_tree，成对恢复 join_rel 状态后以 cheapest_total_path 代价作为 fitness

openGauss · ed99bbde5308942d4eb062e7a851bdb85dda902f · declared-build

审阅状态 independent_review

## 行为和入口
- 函数定义与声明：`Cost geqo_eval(PlannerInfo* root, Gene* tour, int num_gene)` 定义于 geqo_eval.cpp:49，原型在 server/src/include/optimizer/geqo.h；调用方为 geqo() 主循环（每代一次，geqo_main.cpp:190）以及 random_init_pool（后者来自已审 claim，本 attempt 未重读 geqo_pool.cpp）。
- 内存隔离（geqo_eval.cpp:56-70）：`mycontext = AllocSetContextCreate(CurrentMemoryContext, "GEQO", ALLOCSET_DEFAULT_MINSIZE, ALLOCSET_DEFAULT_INITSIZE, ALLOCSET_DEFAULT_MAXSIZE); oldcxt = MemoryContextSwitchTo(mycontext);`。CurrentMemoryContext 此时是 planner 的上下文（geqo() 不切换上下文），所以 GEQO 是 planner 上下文的子上下文；源码注释明确这是为了 geqo_eval 被调用很多次时不必把临时内存留到语句结束，并保证 ereport(ERROR) 中止时也能随 planner 上下文释放。
- PlannerInfo 状态保护（:72-90）：`savelength = list_length(root->join_rel_list)`；`savehash = root->join_rel_hash`；`AssertEreport(root->join_rel_level == NULL, MOD_OPT, "")`；`root->join_rel_hash = NULL`。注释说明：gimme_tree 会把新连接关系追加到 join_rel_list（假设只能追加在末尾），并在需要时局部重建 hash 表，所以评估后必须按长度截断、恢复原 hash 指针；join_rel_level 本不该在使用中，只做断言。
- 评估与 fitness（:92-101）：`joinrel = gimme_tree(root, tour, num_gene)`；`fitness = ((Path*)linitial(joinrel->cheapest_total_path))->total_cost`。fitness 是总代价（total_cost），只取 cheapest_total_path 列表的第一个元素；代码后有 XXX 注释说明 GEQO 目前不支持部分结果检索（cursor 类）优化。
- 恢复与回收（:103-113）：`root->join_rel_list = list_truncate(root->join_rel_list, savelength)`；`root->join_rel_hash = savehash`；`(void)MemoryContextSwitchTo(oldcxt)`；`MemoryContextDelete(mycontext)`；返回 fitness。
- 与最终路径的区别：geqo() 收尾时直接调用 `gimme_tree(root, best_tour, pool->string_length)`（geqo_main.cpp:230），不经过 geqo_eval，因此该次构造的 RelOptInfo 不受 GEQO 子上下文回收，best_rel 会留在 planner 的 join_rel_list 中。

## 状态和消费者
- root->join_rel_list：本函数在评估前记录长度 N；gimme_tree 每次 make_join_rel 会追加新连接关系；返回前截断回 N。实现依赖"新增项只在末尾"的假设（源码注释显式说明），如果任何被调方在列表中间插入/删除，长度回滚会破坏真实状态。
- root->join_rel_hash：评估期被置 NULL，使 gimme_tree 内部按需在 GEQO 子上下文重建局部 hash；评估后恢复原指针。若子上下文内建的 hash 表未显式删除，随 MemoryContextDelete 一起回收。
- root->join_rel_level：只断言为 NULL，不写入也不恢复；非断言构建中该检查可能不生效。
- 内存上下文栈：CurrentMemoryContext 从 planner 上下文切到 GEQO，再切回 oldcxt；MemoryContextDelete 释放 GEQO 内全部临时对象。
- fitness 的消费者：geqo() 把返回值写入 kid->worth（geqo_main.cpp:190），spread_chroma 依此决定是否替换池中最差个体；池初始化阶段每条染色体的 worth 也取自 geqo_eval（已审 claim）。
- 跨模块影响：调用链进入 optimizer/path 的 make_join_rel/set_cheapest（gimme_tree 内），这些函数会写 root->join_rel_list 并填充 RelOptInfo->cheapest_total_path；本函数是唯一为单次评估成对回滚该状态的封装。计划缓存环境不消费这里的状态（GUC 侧由已审 claim 覆盖）。

## 开发与 review
- 必须保持成对结构：savelength/savehash 的保存与 list_truncate/hash 恢复围绕单次 gimme_tree；不得在两者之间新增可能 longjmp 且不恢复的路径还声称恢复成立。
- 必须保持 join_rel_level 为 NULL：gimme_tree 及其被调方不得给 join_rel_level 赋值，否则断言构建失败、非断言构建行为未定义。
- GEQO 上下文必须是 planner 上下文的子上下文，且正常路径显式 MemoryContextDelete；若改成 TopMemoryContext 或会话上下文，评估循环会持续累积内存直到语句/会话结束。
- fitness 必须在 MemoryContextDelete 之前读取（cheapest_total_path 指向子上下文内对象）；如果要把 RelOptInfo 或 Path 指针带出 geqo_eval，会变成悬空指针。若需要保留计划对象，必须像 geqo() 收尾路径那样在 planner 上下文重建。
- 修改 gimme_tree 使其触碰 join_rel_hash 以外的新 planner 字段时，要同步增加保存/恢复；hash 置 NULL 依赖 gimme_tree 能局部重建。
- review 检查点：断言错误码 ERRCODE/模块 MOD_OPT 是否保持一致、list_truncate 的分配上下文（见未知）、异常路径恢复缺失是否被文档化。

## 测试与未知

## 边界与反例

- geqo() 收尾的最后一次 gimme_tree 不经过 geqo_eval，其结果不会被 GEQO 子上下文删除，反而必须保留为 best_rel
- gimme_tree 内 ereport(ERROR)：恢复/删除语句不执行，join_rel_hash 保持 NULL，内存依赖 planner 父上下文回收
- 非断言构建中 join_rel_level 检查可能被编译掉，此时若调用方违反前置条件不会被本函数阻止
- 若 join_rel_list 的新增项不是追加在末尾，list_truncate 按长度回滚会删错条目（当前仅由注释约束）
- GEQO 不支持部分结果检索优化（源码 XXX），对 cursor/部分取值的计划不能期望 GEQO 给出最优
- list_truncate 的分配上下文未验证：若它把 List 头分配在 GEQO 子上下文，随后 MemoryContextDelete 会使 root->join_rel_list 悬挂

## 不变量

- 每次 geqo_eval 的 join_rel_list 长度保存与截断、join_rel_hash 保存与恢复都必须成对
- gimme_tree 及其被调方只能向 root->join_rel_list 尾部追加（源码注释假设）
- gimme_tree 运行期间 root->join_rel_level 必须为 NULL
- GEQO 上下文必须是 planner 上下文的子上下文，并在正常路径删除；fitness 必须在删除前读取
- 不得把子上下文内的 RelOptInfo/Path 指针作为返回值带出（返回值只有 Cost）
- 评估期间 hash 置 NULL 的前提是 gimme_tree 能在局部重建 hash
