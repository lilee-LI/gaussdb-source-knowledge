# 机制：局部断言、失败谓词与清理边界

openGauss · content-addressed · linux-native

审阅状态 依赖已变化，待复核

机制：GEQO 的局部错误分三层。(1) 合法性问题：make_join_rel 返回 NULL 时 merge_clump 直接继续搜索，force 不会绕过它；这是正常控制流，不是错误。(2) 可恢复的交叉失败：gimme_tour 在当前点无未用边时 edge_failures++ 并走 edge_failure，仍能返回下一个 gene；_failures 只用于统计。(3) 内部不变量失败：gimme_gene 的 minimum_count 未设置、无共享边/最少边候选、edge_failure 三层兜底均失败、gimme_tree 最终 clump 数不为 1，都会 ereport(ERROR, ERRCODE_OPTIMIZER_INCONSISTENT_STATE；此外 geqo_eval 用 AssertEreport 检查 root->join_rel_level==NULL，它不保存/恢复该字段，条件失败时先 Assert 再 ereport(ERROR, ERRORCODE_ASSERT_FAILED)（Assert 的具体反应依构建）。清理边界：geqo_eval 的临时上下文挂在 planner 上下文下，ERROR 时随父上下文销毁；但 geqo_eval 的错误路径没有正常返回的状态恢复保证（join_rel_list/join_rel_hash 不保证还原），不能要求 ERROR 后同一 PlannerInfo 继续复用。geqo() 已分配的池/momma/daddy/边表没有局部 PG_TRY 清理，依赖语句级 planner 上下文回收。

## 适用条件

- ERX 是当前唯一活跃交叉
- 所有 ERROR 均发生在规划阶段，未执行任何 SQL
- geqo_eval 的 join_rel_level 只检查不保存/恢复

## 边界与反例

- 把 edge_failures>0 当作硬失败是错的：它只计数，函数仍返回 tour
- 把 force 当作绕过合法性是错的：make_join_rel 返回 NULL 仍不合入
- 把 join_rel_level 当成会被保存/恢复，或要求 ERROR 后同一 PlannerInfo 继续复用，会误判 geqo_eval 的错误边界
