可将 join.sql 与 single_node_join.sql 中“multiple degenerate IN clauses”用例复用为 GEQO 回归基线：在 GEQO 分支内设置 geqo = on 与 geqo_threshold = 2，执行同一 tenk1 多重退化 IN 查询，并观察返回 count 结果与事务回滚行为。预期来源为 server/src/test/regress/expected/single_node_join.out 第 2145-2170 行的存量预期文本，其中普通与 GEQO 查询各预期 count=1。执行该基线依赖完整回归测试表与数据初始化（至少 tenk1、int4_tbl、float8_tbl 处于回归初始化状态）、真实规划门控生效（geqo 与 geqo_threshold 设置实际作用于规划器）以及相应平台/节点构建可运行回归套件。execution_status=not_run：本次未执行 SQL，未运行回归，未产生任何实跑结果。与索引 partial 的区别在于：上述引用是完整源码区间及 expected 文件区间，不是运行产物、索引片段或执行记录；复用该基线也不能替代 ERX 别名、pool 排序、临时上下文等白盒测试。

适用条件

  • 必须准备并初始化完整回归测试表与数据（至少 tenk1、int4_tbl、float8_tbl），使脚本中的子查询与计数语义可对照 expected。
  • 必须在真实规划门控下运行 GEQO 分支，即 geqo = on 与 geqo_threshold = 2 实际影响规划器，而非仅存在于脚本文本。
  • 需要可构建并可运行回归套件的平台/节点环境，并按脚本的事务边界（join.sql 的 start transaction / single_node_join.sql 的 begin 与末尾 rollback）执行和比对。
  • 预期对照仅使用 expected/single_node_join.out 的存量 count=1 文本；若环境或平台导致合理差异，应另行判别，不得把本次未运行当作通过。
  • 该基线只覆盖端到端多表退化 IN 的回归层面；ERX 别名、pool 排序、临时上下文等白盒行为仍需独立测试。

边界与反例

  • 若回归数据未初始化或 tenk1、int4_tbl、float8_tbl 缺失，则基线无法按 expected 对照，复用条件不成立。
  • 若 geqo 或 geqo_threshold 被构建/平台配置覆盖而 GEQO 分支未真正进入 GEQO 规划，则仅得到非 GEQO 结果，不能作为 GEQO 基线证据。
  • 若实际输出与 expected/single_node_join.out 的 count=1 不一致，则说明基线对照失败或环境差异，需调查而非判定通过。
