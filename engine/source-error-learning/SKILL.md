# 错误与断言专题研究

执行协议：unified-skill/v1。先读[共同协议](../../references/unified-skill-protocol.md)和[专题扩展合同](../../references/unified-topic-contract.md)。当前任务使用统一引擎；下述方法保留深度，旧手册中的任务/发布命令和客户输出规则仅用于已绑定旧项目。

把一个错误码学成一条可追溯的链：**错误身份 → 检测点 → 上游成因 → 现网场景 → 判别证据 → 有条件处理 → 业务复验标准**。报错行只是起点，错误码不是根因。最终既要解释数据库原理，也要帮助现场人员判断自己属于哪种情况、补什么材料、满足什么前提才能处理。

当前研究使用统一 source_only 合同与 errors 专题扩展；完整盘点继续执行因果、适用性和源码闭合检查。`error-causal/v1` 等旧 study 参数仅由原绑定项目使用。不连接数据库、不运行 gsql/SSH、不执行采集和变更；SQL、场景与处理步骤均为源码推导设计，`execution=not_run`，现场结论为 `not_assessed`。旧任务与已有实验保留其原状态，不能因更新 Skill 自动获得新质量认证。

完整新任务同时启用 `applicability_required: true`：集中式/分布式、宏与构建、节点角色、八领域依赖和传播恢复都是必检项。这些是专业证明义务，统一任务由宿主按范围显式选择并记账；历史任务不追写。先按[适用性规程](../../references/error-applicability.md)建立条件组合，再读整条因果链。

## 版本与证据（完整学习必读）

按[源码版本与共享证据](../../references/source-version-evidence.md)固定不可变源码身份，构建/节点条件独立记录。当前统一研究使用快照/profile/evidence 与知识修订绑定；source-evidence/v2 等原合同只用于旧项目。源码按内容哈希共享，证据只存定位、片段哈希和用途。Wiki 用简短关键片段与结论解释，长源码不复制到 Markdown；换版本先做依赖变化评估并实际复核，不自动继承适用范围。旧凭据保留原字节。

## 先选择任务

- **完整学习一个错误码**：执行下列全部阶段，产出因果研究表和可读 Wiki。不要拿一个签名附近的窗口代替全流程。
- **补已有知识的缺口**：先读适用版本的已发布文章及研究记录；明确补哪些检测点、分支或场景，创建新任务并引用旧知识。覆盖声明只针对本轮范围。
- **回答一次现场报错**：先检索已发布知识，用已知证据给可支持的判断和最小采集；发现缺口才扩展研究。不要让简单问答默认重跑全库学习。

三个使用场景分别对应共同协议中的 survey / mechanism / reference；一次现场问题优先查询已有知识。当前命令见[统一运行手册](../../README.md)。CLI 管理任务、证据、状态，宿主实际研究与审阅。原[使用与契约](references/error-causal-contract.md)仅用于旧绑定项目。

批量学习多个错误码时按[并行学习规程](../../INTERNAL.md)创建机制依赖与独立任务，使用原生调度器或宿主授权的多Agent分工。每个研究者输出完整因果与适用性结果，独立审阅后统一编译；共享机制不复制，未知前置不放行。

## 一、界定错误身份与范围

任务包含断言或混合检查时，先读[GaussDB双分支执行手册](../../INTERNAL.md)的共同主干与断言分支。没有产品编号/SQLSTATE可标不适用或未知；内部知识ID不冒充产品号。额外完成宏展开/极性/求值、不变量、相关写者/生命周期/并发、实际失败控制流和未启用后果的研究与审阅，不能只沿用普通ERROR的清理结论。

1. 固定产品、版本、源码 revision、快照、构建开关和研究入口。公开 openGauss 只能证明所绑定版本；内部 GaussDB 的对应关系未知就明确保留未知。
2. 分别解释 GAUSS 编号、SQLSTATE、主消息、DETAIL/HINT、严重级别。GAUSS 手册目录号与构建实际返回码不能混同；SQLSTATE 是五字符状态标识，写出其中文含义并绑定映射依据。
3. 交叉检索编号映射、消息固定片段、SQLSTATE 枚举、包装宏、调用者和近邻错误。记录检索式、范围、排除项与限制；同一编号/消息的多个检测点全部建账。
4. 选择本轮对象，列出未绑定的别名与未分析候选。存在歧义时按候选分支研究，不能把第一条命中当成唯一实现。
5. 建立集中式/分布式检查及相关 variant 表；核对文件入选、宏定义与覆盖、角色/连接来源、参数生效时机和 ABI。未知目标构建可输出条件结论，但不能按宏名推产品、把 unknown 当关闭或合并不同组合的代码路径。

## 二、先还原正常机制，再解释检测点

对每个检测点从实际入口读到返回：SQL 解析/绑定或工具入口 → 参数与状态构造 → 关键状态迁移 → 检测 → 输出/清理。记录：

- 正常允许什么、维护什么不变量，为什么需要这项检查。
- 真正的函数签名、类型/重载、参数默认值和前置护栏。
- 完整失败谓词、短路与分支顺序、宏展开、编译与兼容模式条件。
- 报错前已经发生的写入或外部副作用，异常等级、事务状态、资源所有者和清理路径。
- 不能到达此点的近似输入，以及会走其他错误的相邻边界。

不能从目录名、注释或单个 if 直接推断行为。断言必须追不变量的全部相关写者、生命周期与并发保护；关闭断言不能作为修复。

## 三、从检测条件反向追多条成因，再正向核实

对检测表达式中的输入、状态、返回码逐个追生产者/修改者/调用者，至少读到能解释该值如何形成的上游机制，再正向检查路径可达性、护栏和清理。明确三个层级：

1. 检测到的直接状态。
2. 能形成该状态的上游机制成因。
3. 现场业务如何形成该输入/状态的候选来源，需什么材料才能确认。

按相关轴展开：入口、输入/类型、NULL/边界、兼容与配置、事务快照、并发顺序、对象/权限、资源、工具参数、WAL/解码状态和构建差异。仅展开会改变失败路径、判别或处理的组合；不机械凑原因数量，不把同一成因的十个值当十条根因。

每个成因必须有检测点引用、逐步因果链、源码证据、前提、最近竞争解释与区分事实。源码无法证明就写假设及缺口，不升级为已证实根因。跨领域依赖须提出具体问题，读取状态生产者；普通关联链接不算闭合依赖。

对兼容、等待、视图、内存、工具、解码、事务并发、对象权限逐项登记必要/不涉及/未知。依赖分成因、观测、恢复、适用性四类，绑定点/成因/采集/措施与 variant。跨节点或异步路径追首发错误、包装转发、客户端呈现、取消回滚及清理所有者；本地恢复不能代替远端恢复证明。

## 四、将机制翻译成可区分的现网场景

每张场景卡说明：谁从什么入口、在何条件下看到何种现象，对应哪些候选成因，容易和什么混淆，下一项证据将怎样改变判断。多个成因可共存，不强制互斥。

每个判别项都有**支持、排除、未知**三种结果。采集缺失、权限失败、NULL、采集太晚、换会话或节点均不能当排除。观察到失败状态不等于证明其历史来源；一个阻塞候选不等于完整阻塞链。

针对场景提出最小采集集：执行位置/身份/权限、具体命令或应提交的材料、字段、时间窗口、预期形态、代价/隐私、空值及失败含义。先取低成本判别材料，再按分支补充；不能只写“看日志、查视图”。不确定版本支持的 SQL 时，保留采集缺口，不伪造可执行语句。

## 五、按成因给有前提的处理方案

分别考虑恢复业务、临时规避、持久修复和防复发。每项措施写明：

- 适用场景/成因、必须已经获得的支持证据、排除条件和证据未知时的退出。
- 操作对象、身份/负责人、具体步骤，预期改变哪条状态或输入链。
- 业务语义不变量、数据/事务影响、权限/并发影响、回退及失败出口。
- 复验标准至少覆盖“错误触发条件消失”和“业务结果正确”，必要时加副作用与复发检查。

不能简单将 if 取反当方案。删除字符、默认填值、截断/转换、重试、调大参数、改对象/权限、杀会话或重启都要独立证明适用前提与语义安全。错误消失但金额、事务效果或数据完整性不正确，属于处理失败。

没有安全措施或尚不能区分时，明确写“待补证/源码缺口/暂无安全操作”，给出具体下一步；不要为了填表输出破坏性建议。

## 六、用反例检查覆盖，并编译 Wiki

每个源码支持的成因都要有触发案例和最近正常反例；每个可处理场景还要有不适用措施/错误措施的反例。案例从分支推导，不执行、不编造实际输出。相同消息的其他检测点、其他成因、相邻错误、证据过期、多个成因并存均需按相关性挑战。

原有 `error_analysis` 的身份、检索、检测点、成因、场景、判别、采集、措施、案例和逐点覆盖继续保留；与 `source_analysis` 对应的共同路径、规则及跨领域依赖使用同一组统一证据/知识。当前将专业结构保存到 topic_extensions.errors.details，或作为冻结文档证据引用；旧字段中的 evidence ID 需实际重新绑定，不能只改格式。结构检查后仍须逐项真实审阅，自查标 `self_reviewed`。

需要构建/角色专项账时，可沿用 [error-applicability/v1](../../contracts/error-applicability-v1.schema.json) 的专业维度：构建变体、八域依赖、逐对象适用性、传播恢复和差异反例。当前按 topic_extensions.errors.details 保存，或引用冻结文档，不创建旧发布状态。专业表不能用摘要代替；正文展示适用条件与依赖影响，开放依赖只限制相关组合。

Wiki 面向读者组织，先说明码和术语，再给原因导航与诊断顺序、各场景采集及有条件方案、源码推导案例和边界，源码依据放最后。正文引用已接受研究中的成因/场景 ID；一个主文章可链接独立场景/机制/处理规程，但读者不能必须先读结构化 JSON 才能使用知识。

源码依据放最后不等于只保留结论：可读Wiki必须展示真实入口调用链、关键对象/字段的生产与迁移、完整失败谓词及分支次序，各成因写清生产者→状态变化→消费者→检测。保留帮助理解的原样短源码和精确版本/函数/路径/行号；长文件留证据仓。按[读者Wiki交付要求](../../references/reader-wiki-contract.md)将最终wiki和过程.work分开，关闭研究/JSON后回读验收。机器证据、检查表和“需要更多材料”不能代替已经能从源码解释的机制。

当前通过统一 task submit/review、knowledge propose/review 及内部母包 publish/verify 交付；旧 study/article/stage/release 链只用于原绑定项目。开发交付检测前提及改动影响，测试交付触发/最近反例和预期来源，review 交付保护/传播/清理契约。程序只检查结构、关联、绑定与审阅声明，不证明源码语义或现场效果。报告实际覆盖分母、开放分支、未知依赖与未验证项，不能用“完成一次提交”表示“全库学透”。

## 交付给用户

说明实际绑定的源码范围；展示正常机制和根因树；用表列场景、支持/排除/未知证据及对应措施；说明源码额外揭示的边界；给出主 Wiki、研究表和未闭合项路径。已有设计和手册主动纳入对齐；缺失、草稿、不同版本与文码冲突分别保留，不能拿文档声明代替实现证明。不改 GaussDB Agent 前端，不连接真实数据库来充当本次 Skill 验收。

## 移植到另一源码产品

先读可迁移学习体系（旧版资料）。本工程错误发现使用项目 adapter 的 markers/extensions/source_globs/catalog_paths；不能仅替换 product 名称。编号与 SQLSTATE 可未知或不适用，记录映射限制并按消息/位置继续研究。新完整任务启用源码闭合账，按声明范围区分 complete_within_scope 与 partial。

需要独立迁移时使用白名单导出的 source-error-learning 专用包，包含自身方法、模板和可选标准库证据校验器。它不要求主工程 CLI、Node/npm 或外部领域 Skill；完整工程的任务审核发布是可选集成路径。迁移方法后，GaussDB 的事实须重新用内部源码锚点证明。
