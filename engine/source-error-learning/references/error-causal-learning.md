# 错误码因果学习规程

## 研究单位与证据边界

错误码是检索入口。研究单位是绑定版本上的“错误家族”：编号/SQLSTATE/消息及其检测点、入口、可达分支和相关正常机制。一个编号可关联多个点；一个点可由多个机制成因到达；同一机制可由不同业务来源触发。现场真实根因需要现场证据，源码只能给出条件关系。

开始先写研究边界：产品、revision、快照、入口、构建对应程度、已知对象、排除项。目录号映射若只有手册/历史 Wiki，标 alias_only；实际构建与源码未绑定时不写“该版本必返回 GAUSS-xxxxx”。SQLSTATE 也不是单个函数或唯一根因。

本流程 source_only。不得连接实验库、SSH 或生产环境；所有采集、措施和案例保持 not_run。源码推导的预期不能伪装成实验实际输出。

## 1. 找全本轮声明范围内的检测点

交叉检索至少覆盖编号映射/消息固定片段/SQLSTATE 标识/包装与调用路径，记录实际搜索的范围、式子、结果解释和限制。编号不存在于代码时，要从可核验的映射和消息继续定位，而不是宣布“源码没有此错误”。动态消息、翻译、宏、多行调用、生成目录及分支构建均可能造成漏检。

建立检测点表：ID、函数及文件、主消息和 DETAIL/HINT、级别、条件、前后副作用、清理、关联 claim/evidence、分析状态。相同消息不同位置不要合并成一个点；同一位置不同分支可以共用点 ID，但必须保留不同条件。仅注释或不可达示例不计实际候选。

候选搜索范围不等于全仓库证明。完整性只针对声明范围，开放候选须有下一步；不要给“已穷尽全部根因”的无界结论。

## 2. 解释正常机制与不变量

先回答：数据库原本想完成什么？哪项不变量保证成功？失败检查为什么在这里？实际入口如何绑定到这个重载/函数/工具阶段？

按入口至效果阅读：解析/绑定 → 输入整形 → 上下文与配置 → 状态生产 → 检测与分支 → 结果消费 → 退出。针对关键点保留足够源码，不预设固定行数。至少核对调用者、被调函数、相关宏/常量、状态定义与写者；在并发/事务场景补锁保护、快照和生命周期。

每段调用证据核对最近外层函数与路径身份，不能把另一函数中的相似循环当作目标入口。进入关键循环之前的快速路径、提前 return、NULL/strict 分派以及错误捕获同样需要检查；尚未展开的分流记为开放项，普通路径结论不得扩大为全部入口。

记录正常输出与持久/临时副作用、报错前已做的事情、ERROR/FATAL/PANIC/断言差异、资源释放和事务是否仍可继续。说明“原语句失败”“事务中止”“连接退出”之间的区别；没有证据的范围不要推定。

## 3. 反向切片与正向可达检查

以完整失败谓词为起点，逐个追表达式操作数。对输入追入口、转换、类型、默认值及源数据；对状态追初始化、修改者、所有权和时序；对返回码追内部失败条件。遇到包装层继续展开直到足以区分原因，不能把“底层函数返回失败”作为最终解释。

再沿每条候选路径正向验证：是否已被上层检查拦截？走到的是同一重载吗？模式/编译开关使分支可达吗？报错参数确实来自此变量吗？中间是否清理/重置状态？是否有并发窗口？如果应先触发另一个错误，就不能算当前检测点的有效案例。

| 层级 | 应写内容 | 不能替代它的表述 |
|---|---|---|
| 直接状态 | 检测表达式观察到哪个不变量被破坏 | “出现此报错” |
| 机制成因 | 哪条输入/状态链使检测条件成立 | 原样翻译 if |
| 业务来源候选 | 应用/工具/数据/并发如何形成该输入，需要什么材料确认 | 把一种常见应用问题当客户已证实事实 |

成因卡至少包含：点 ID、入口与前提、两步以上实质因果链、逐步源码、现象、最近竞争解释、最小区分事实、已知边界。两步只是结构下限，不能靠重复同义句过关。源码支持的关系标 source_supported；尚有推理跳跃标 hypothesis，并写缺口及精确下一步。

## 4. 按相关维度展开而非堆案例

| 维度 | 要追的问题 |
|---|---|
| 入口/阶段 | 直接 SQL、绑定参数、COPY、导入工具、解码插件是否在同层触发？ |
| 输入/类型 | 文本/二进制、显式/隐式转换、类型重载、NULL/空/边界、编码如何变化？ |
| 兼容/配置 | 取值在哪层读取，优先级与会话作用域是什么，改变后走哪条分支？ |
| 事务/快照 | 语句和事务隔离、失败后的状态、重试边界、可见性怎样影响错误？ |
| 并发/等待 | 已授予冲突、队列、公平性、超时/取消/死锁如何分别到达报错？ |
| 对象/权限 | 名称解析、schema、临时对象、ACL、对象依赖/变更是否影响可达性？ |
| 资源/内存 | 分配者和所有者、限额/实际不足、节点/线程范围和清理是否不同？ |
| 工具/解码 | 参数组合、事务/快照、WAL/slot 位置和重启恢复能否解释现象？ |
| 构建/版本 | 分布式与单机、功能宏、版本差异是否使同名错误不等价？ |

只展开改变根因、判别或措施的组合，不做所有轴的机械笛卡尔积。相同成因下不同数值通常是案例，不是独立根因。真正只有一个成因时明确给出证据和排除范围，不强凑多分支。

## 5. 闭合领域依赖

对兼容性、等待事件与耗时分析、系统视图、内存上下文、导入导出和逻辑解码逐一判必要性。需要的依赖写成可回答的问题，例如“该视图此字段是当前状态还是累计值”“该模式在解析层还是运行层读取”，随后读定义/生产者/消费者并引用证据。

依赖可在本任务内闭合，也可引用已接受的精确版本研究；未闭合就保留 open 并限制结论。加链接、读一份领域概述或把任务指派给某团队，都不等于依赖已完成。

## 6. 从因果图转为现场方案

按[场景与处理规程](field-scenario-playbooks.md)生成场景、判别、采集和措施。每条措施能逆向解释：改什么状态 → 切断哪条因果链 → 在何条件下消除该失败 → 如何保证业务意义不变。如果无法解释这四步，就只是待研究提案。

最终检查每个声明检测点是否有成因与场景、每个已支持成因是否有触发和最近正常反例、可处理场景是否有判别与安全措施。覆盖表保留 open/out_of_scope；它是带分母的研究账，不是自动“充分性分数”。
