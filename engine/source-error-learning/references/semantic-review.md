# 发布前语义质量复核

语义复核判断“这份知识是否能解释、区分并指导处理”，结构校验判断“数据、引用和绑定是否符合契约”。两者分别记录。现有 `submit`、`study.review`、`article-review` 或 `publish` 不自动完成语义判断。`article-review` 保存 Agent/人实际审核的逐项意见并检查完整性；`independently_reviewed` 等身份字段只是声明，不能据此虚构独立人审或专家背书。

## 审核输入、过程和输出

审查者至少读取最终文章、当前 V2/study、冻结源码的相关完整函数/定义/调用与写入/清理路径、采集及解析实现/原始样本、已有验证记录和未完成清单。不能仅看生成页面或提交摘要。在没有独立审查者时可先自查，明确标为自查；不为完成进度填写另一名 reviewer。

每条审核意见必须包括：被审知识/文章哈希、问题或通过的具体命题、证据位置、判断及修正/补证要求。按下述 article review v1 保存机器记录，可另附 Markdown 说明实际查阅范围、源码/原始材料证据及待办；不要向严格 V2/study schema 塞审核字段。

- 审核人/Agent 身份、是否作者、实际审阅材料和时间。
- `structure`：pass/fail/未运行，附真实校验回执。
- 知识结论：合格/限定范围合格/退回，以及逐项判断、严重缺陷和限制。限定范围合格仍须全部八项标准在声明范围内通过，机器 decision 为 accepted_for_diagnosis；存在 fail/unknown 则为 research_only。
- 源码分析成熟度、采集实现和实测、措施运行记录、人审状态及 A/B 实验分别报告；没有对应记录就写未做。
- 拒绝/待改项逐一关联新修订，修订后检查影响范围，不能只修改一段措辞就沿用旧审核结论。

限定范围合格要求限制写进标题/开头和检索输出，且不存在会令所声明范围内诊断或措施错误的缺陷。关键因果仍缺失的局部分析可作为调查草稿保留；不得被计入“诊断知识合格”数量。客户根因尚未确认与文章知识不合格是两回事：合格文章应允许证据不足时正确保持未知。

## 已实现的审核 JSON v1

`article-review --snapshot SNAPSHOT --site SITE --review FILE` 接受且只接受 `schema_version, binding, article_sha256, reviewer, mode, criteria, decision, limitations`。

- `schema_version` 为整数 1；binding 与当前知识一致，article_sha256 指已提交文章的确切内容哈希。
- `mode` 为 self_reviewed/separate_agent_reviewed/human_reviewed。分离 Agent 审核须声明与文章作者不同的 reviewer；字段不能证明独立会话或真实人审，实际过程另留证。
- `criteria` 必须恰好包含 causal_depth、discriminating_evidence、executable_collection、evidence_interpretation、conditional_remedies、verification_and_limits、source_traceability、reader_usability。它们依次检查因果深度、原因判别、采集可执行、证据解释、有条件措施、复验/限制、源码追溯及文章可读可用。
- 每项恰好含 status（pass/fail/unknown）、finding（具体判断与依据/补证）、article_quote（当前文章内确切连续原文）。引用只是定位，不是证明；finding 应说明核查了什么关系以及为什么通过/失败。
- `decision` 为 accepted_for_diagnosis/research_only。accepted_for_diagnosis 只接受全部项目 pass；任何 fail/unknown 留为 research_only。`limitations` 为非空文字列表，即使全部通过也写明版本、范围和未做实验/审核。

程序逐项检查绑定、枚举、必需项目、文章引用及 decision 一致性，不验证判断真实性，也不会因为文章含八个标题和 SQL 就自动判知识合格。审核记录不可变，显式选择当前活动文章；文章/知识变化不继承原审核。源码分析完成度、实际运行与人审身份仍独立记录。

## 逐项标准和否决条件

| 项目 | 合格的可核查标准 | 应退回的具体情形 |
| --- | --- | --- |
| 身份与签名 | 产品/源码/构建映射及模式已列明；同码多点、目录候选和实测映射有区分 | 把公开产品映射直接改名；只凭文案锁定唯一位置；构建未知却下精确结论 |
| 正常机制 | 可以解释合法状态为何成立，谁产生/修改状态、生命周期/同步/权限/类型等相关约束 | 只有 if 翻译；读者仍不知道输入/状态从哪里来 |
| 因果与可达性 | 每个原因有实际入口与前向路径；关键写者、前置护栏、构建/兼容分支和传播/清理经过检查；停止边界具体 | 将已被上游拒绝的输入编成目标点原因；把检测位置当状态破坏位置；只读报错前后几行就称完整 |
| 原因区分 | 每个原因有支持/排除/未知条件，并与最近竞争解释用真实可观测差异区分 | 所有原因共用“报错了”作为证据；缺少记录被解析成 false；出现多个支持分支却强选一个 |
| 采集可执行 | 原角色/实例/事件关联、SQL/工具参数、目标版本、权限、时间、输出及失败处理明确；生产与解析分别标实际能力 | 只写视图名/工具名；让客户填根因布尔值；管理员晚采结果被当作失败时刻的事实 |
| 措施正确性 | 每项措施解释作用点、独立前提/禁止条件、业务影响、步骤、回退及复验；运行状态与证据一致 | 原因成立即无条件授权；建议重试却没核对事务/幂等；改宽结果类型却未检查中间类型；关闭断言作为已证实方案 |
| 验证诚实 | 真实输入与 before/after/结果/负例可核对；失败、不确定及未运行均可见；每个措施独立计数 | fixture/条件匹配冒充数据库实验；一个成功推及全码；只看不报错，未检查值/类型/业务语义 |
| 文章可用 | 先解释错误码、中文含义及关键术语，再连续走到原因、补采、条件方案和复验；源码位置与深入实现放文末，并可回溯支撑的说明 | 用未解释的SQLSTATE/缩写/内部参数开场；源码行号淹没主要解释；只增术语表却仍以压缩字段代替原因和措施 |

任何会造成错误根因确认、失真版本适用或无前提措施的缺陷都是阻断项，整体判 rework。拼写、排版和非关键链接可以作为普通修改项；不能用平均分抵消阻断项。缺乏相关材料时不写通过，写“未核对及需要什么”。

## 用反驳检查推理，而不是按标题打勾

对涉及现场判断或事务动作的文章/答复，补用 [证据边界与恢复审查](evidence-and-recovery.md)：晚采不能回溯、空结果不能跨时段排除、NULL 不凭概述推定矛盾；逐连接核对动作资格，并遍历每次失败、观察失败、中止和最终收尾。适用规则依机制选择，不把事务流程强套到所有报错。

审查者应从知识自身的因果链选择有区分力的问题；不机械要求固定数量原因或所有错误都覆盖全部数据库领域。

1. 把被声称的原因替换成最接近的竞争解释，现有原始证据和采集能否区分？如果不能，结论是否保持未知并给下一步？
2. 从真实 SQL/状态写者向前走一次，是否经过会拒绝该输入的护栏？从 ERROR 向后走一次，状态/锁/事务会怎样改变，事后证据是否仍存在？
3. 将一个必要信息替换为缺失、过期、错会话或相反信息，诊断是否停止确认，相应措施是否被阻止？
4. 原因成立而业务前提不成立时，措施还能被错误地推荐吗？是否检验结果值、对象身份、类型、并发或副作用，而不只检查报错消失？
5. 证据足够时是否明确给出相应强度的原因和阶段结论？完整客户记录可以支持注明条件的充分原因；历史唯一性未知或防复发调查未完成，不能把已证实的本次恢复退回“整体未闭合”。没有执行 after 也不能把方案通过称为案例闭环。

这些可以通过源码推演、真实记录或隔离实验核对，记录各自的证据类型；推演不能被登记为运行成功。首次验收先闭合已学习机制，不将未知新主题迁移能力设为本轮必过条件。

## 典型审核结论

不合格结论：“字段齐全，锚点校验成功，bounded，文章可发布。”这是结构结果，没有回答知识是否可靠。

合格的退回结论：“结构通过。知识退回：文中将 NOWAIT 后无等待行作为没有冲突的排除证据，但所读清理路径会移除请求；当前快照晚于报错。删除该排除结论，补同对象、锁模式及失败时段轨迹；拿不到时保留历史持锁者未知，并阻止取消特定会话的提案。原有运行记录只验证报错及重试，不证明该持锁者身份。”实际审核需附该版本源码与原始文件锚点，不能只借用示例作为事实。

合格的有限通过结论：“结构通过。知识在所列未限定关系名路径及构建内合格；已核对有效路径、权限和身份差异，原始材料可重建判定。其他关系入口未纳入，内部 GaussDB 构建映射未做，文章开头及检索输出均保留限制。采集已实测，长期配置修改尚未运行；文章未将其写成已验证措施。审核为作者自查，独立人审未做。”

## 发布门槛

可先将未合格成果保存为明确标记的研究草稿，便于协作，不计为最终诊断知识。正式交付最终文章前必须保存本文逐项语义审核及结论；自动生成、结构通过和 Wiki 写入成功都不能替代它。措施运行实测、人审独立性和 A/B 诊断实验是另外的证据维度，不要求没有人审或无法实验时造一个通过状态。

生产者、解析器、源码/构建、文章或关键因果/措施改变后，复核受影响部分。文章与审查记录绑定当前知识；旧审核、旧实验保留历史，不自动给新版本背书。
