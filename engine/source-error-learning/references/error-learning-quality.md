# 错误码学习与 Wiki 的质量标准

版本化证据新增两项完整任务自查：`source_version:binding_and_patch_scope` 核对提交/补丁/选择范围与构建角色独立；`source_version:dedup_and_knowledge_scope` 核对共享证据、关键片段、逐结论适用范围及新版本未复核状态。详见[版本规程](../../../references/source-version-evidence.md)。不能只刷新哈希或复制旧文章宣布跨版本适用。

## 研究审阅：逐项给出发现

结构检查检查表、ID、引用、覆盖、状态和源码绑定；不会判断 C++ 语义、查询能否区分原因、措施会不会损失数据。审阅者必须实际阅读研究、源码和反例，自查使用 self_reviewed，只有真实独立审阅才用 independent_review。

| 检查 ID | 审阅者要回答的实质问题 |
|---|---|
| error_causal:identity_and_sites | 编号/SQLSTATE/消息是否混同？交叉检索遗漏了哪些点？构建与版本有何限制？ |
| error_causal:upstream_causes | 是否真正追到输入/状态生产者？护栏和调用顺序是否使此链可达？是否只是改写 if？ |
| error_causal:field_scenarios | 场景拆分是否改变判别/动作？是否漏掉入口、模式或并发差异？是否把机制当客户事实？ |
| error_causal:discriminating_evidence | 原始输出能区分最近竞争解释吗？NULL、无权限、过期快照及多因共存怎样处理？ |
| error_causal:conditional_remedies | 每项措施是否有独立前提、排除、具体步骤、负责人、回退和失败出口？ |
| error_causal:semantic_safety | 错误消失后业务意义是否仍正确？重试幂等/事务/副作用是否闭合？ |
| error_causal:counterexamples | 是否有最近正常、竞争路径、错误措施及前提不足的案例？期望确实由源码推出吗？ |
| error_causal:coverage_and_gaps | 分母是什么？是否有未列出的候选？所有 open/out_of_scope 都有可执行下一步吗？ |
| error_causal:source_vs_field | 是否把静态推导、结构检查或自查写成真实观测/实测/独立人审？ |

不能使用九段相同的“已通过”作为实质审阅。每项写出所检查的对象和具体发现/限制；不适用也需证据及原因。存在未证实因果、不可区分原因、无前提危险措施或虚构运行结果，结论必须 reject 并修订。

## 文章审阅

| 检查 ID | 要求 |
|---|---|
| error_causal:cause_navigation | 先解释错误码、主消息与术语；原因导航能让读者知道不同分支，而非裸源码链接 |
| error_causal:scenario_decisions | 场景、支持/排除/未知条件和具体采集可直接阅读，与研究 ID 对应且不夸大 |
| error_causal:remedy_boundaries | 针对不同成因的措施有前提、语义约束、影响/回退和业务复验；缺口清晰 |
| error_causal:reader_evidence | 核心说法能追到已接受研究/源码；源码置后；版本、覆盖和未运行状态醒目 |

文章先讲“这是什么”，然后“可能为什么、我怎么判断、怎么有条件处理”。SQLSTATE 先翻译，NOWAIT、隔离级别、typmod、slot 等首次出现时解释。不要让读者按源码顺序阅读十几个文件才能获得处理逻辑。

主文章可以链接场景、机制与规程页，但主文章至少提供原因/场景导航与适用边界。研究引用 ID 只是定位，不是正文已经充分呈现的证明。

实际回读还须核对：Wiki里能否找到真实入口调用链、关键状态的生产者与消费者、完整失败条件、逐成因的可达路径及必要原样短源码。只有字段名、源码路径列表、研究引用或一张概括表，不算充分呈现实现。关闭研究和JSON，仅靠Wiki回答原理、分支、场景和条件方案；答不出则补学重写。最终知识和过程文件分目录，不把检查报告/JSON混入阅读入口。

## 对抗检查清单

完整新任务还须逐项审阅[构建、角色与跨域适用性](../../../references/error-applicability.md)，另记录以下发现，不以旧九项概括代替：

| 检查 ID | 实质问题 |
|---|---|
| error_applicability:build_and_macros | 集中式/分布式分别如何判定？文件入选、宏定义/undef/覆盖和嵌套条件是否在同一构建下？是否把默认选项当最终值？ |
| error_applicability:roles_and_paths | 角色宏读什么状态，连接来源/线程/参数读取时机是否改变入口和清理？逐点、成因、采集、措施是否绑定相同组合？ |
| error_applicability:domain_interactions | 八域是否逐项有具体问题及依据？生产者→消费者是否已读？开放依赖是否限制下游结论？ |
| error_applicability:propagation_recovery | 首发/报告/观察节点是否混同？包装转发、取消回滚、资源和远端对象的恢复边界是否闭合？ |
| error_applicability:variant_counterexamples | 换宏/角色/配置会否推翻结论？等价合并是否有证据？不可构建与未知是否被误算已覆盖？ |

文章审阅增加 `error_applicability:reader_scope`：读者能否在正文辨认适用产品形态、角色/连接、相关模式及 unknown，以及相关领域怎样改变判断与措施；不能要求先读 JSON 才知道方案只对本地路径成立。

针对相关项实际挑战并记录结论；不相关也说明范围，不机械扩展固定轮数：

1. 相同消息来自另一检测点，当前方案是否误用？
2. 同一检测点由另一状态生产者形成时，现有证据能区分吗？
3. 更早的类型绑定/权限/对象检查会阻止路径吗？
4. 更改模式、输入边界、事务阶段后是否走另一个错误？
5. 多个成因同时存在，修复一项后如何发现另一项？
6. 用报错后的当前配置/视图解释历史状态，会不会误判？
7. 采集返回空或无权限时，规程是否错误排除根因？
8. 处理前提缺失、重试不幂等、字符清洗改变业务值时，是否仍推荐措施？
9. 错误消失但业务结果错误，复验能否发现？
10. 跨版本、跨产品、构建不一致时，是否无依据沿用映射与措施？

## 覆盖与完成报告

按声明检测点逐项记 covered/open/out_of_scope。covered 只说明在声明范围内已有成因和场景，不证明真实世界所有成因穷尽。假设不得冒充已支持成因。开放点、只具假设的场景、无安全动作的场景均计入报告。

不强制某错误至少有 N 个根因，也不用案例数量代替覆盖。如果真实只有一个成因，解释检索与排除范围；如果仍有未读状态写者，明确本轮只得到有限成果。

交付报告应分别列源码范围与映射状态、检测点/成因/场景数量、开放项、真实自查方式、已接受/已发布状态和运行状态。当前 source_only 的数据库执行量恒为零，不能称“解决方案已验证有效”。
