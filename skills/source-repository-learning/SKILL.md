# 整仓、模块与特性学习

执行协议：unified-skill/v1。先读[根入口](../../SKILL.md)和[共同协议](../../references/unified-skill-protocol.md)。本 Skill 决定如何发现、分批和综合知识，任务、证据、审阅与发行沿用 `scripts/unified_kb.py`，不另建状态机。

## 绑定与发现

1. 确认产品、真实提交/内容快照、研究范围、设计与手册状态、构建 profile 和目标母库。公开 openGauss 不自动等于商业 GaussDB。
2. 全树清单保留 SQL、语法、注册、测试、构建和排除/失败项；通过真实前端、词法候选及独立遗漏检查分别记录覆盖。目录与聚类是模块候选。
3. 从用户入口、设计/手册能力、命令/参数注册、状态读写和测试发现特性。历史无设计时恢复实现协议，保留设计理由未知；文码冲突独立记账。
4. 先读适用版本已审知识，区分复用、核对、深化和失效复核。CodeWiki 可提供代码导航或说明候选；已有正确研究不需要无条件重新生成。

## 形成任务与责任边界

默认由 guide 输出全仓模块候选、材料缺口和可领取的盘点任务。focus 选择具体 TU，按需要 integrate 多个模块的图。team 工作单分配到不同服务器，回收后经过中央审阅。显式深度 plan 使用函数/SCC 切片与逐文件发现任务。宿主依据实际路径补充跨模块特性、共同机制、未解析目标和图外行为。循环依赖分片研究后综合，父任务不能凭子摘要跳过关键契约。

责任树 L1 领域、L2 子系统、L3 模块、L4 机制/接口责任单元；特性树 L1 能力域、L2 功能族、L3 特性、L4 行为单元。源码挂到实现与证据位置。主维护方、消费者、特性维护者通过关系连接，不按文件目录认定组织责任已经批准。

对每个特性判断八专题依赖和[内核公共检查](../../references/unified-kernel-research-checks.md)。发现必要的兼容性、内存或错误前置缺口时建立共享机制/专题任务；能够在当前条件下解释的部分单独交付，未解决依赖限制相关结论。

## 研究与综合

读取冻结上下文，按入口→状态生产→变换→消费→出口及正常/异常清理追踪。核对宏、重载、方法表、缓存固化与重算、同步和恢复。逐结论给条件、真实证据、最近反例和开放项。

使用统一租约、检查点和证据回执；截断不算读完，过期租约重新认领并按新租约核对证据。专题深度按 reference / mechanism / survey 选择，方法计划只表示准备完成。

专业成果按[专题扩展合同](../../references/unified-topic-contract.md)映射到统一知识对象；主文讲清实现机制，专业表保持结构，事实和机制通过稳定 ID 复用。方法与产品事实分开，源码预期与实际运行分开。

## 回读、增量与发行

研究提交后实际审阅，再经知识提案及审阅形成修订。回读开发、测试和 review 查询是否能取得条件、跨模块消费者、测试依据及未知；方法或源码变化触发定向复核，不追认旧结果。

统一发行当前是含源码证据的内部完整母包。对外用途另做投影。旧 CodeWiki 批次及客户无源码包继续其原合同，历史执行方法见档案（旧版资料）。历史经验不能自动变成当前能力或当前知识的批准状态。

最终说明实际范围、已审结论、候选/解析/语义覆盖、开放问题和使用验证。当前 source_only，数据库与 SQL 未运行。
