## 耗时口径与故障修复

从首轮启动到 ECS 审计及压缩完成的实际经过时间为 14163.155 秒（3 小时 56 分 3.155 秒），包含中间排查修复等待；最终 ZIP 为 925,892,885 字节。网络复制及 Windows 工作另计。

首轮使用 2.1.0，完整命令从新工作目录开始计时，包含冻结材料、分析、入库、跨文件绑定、导出及校验；不包含此前已完成的 Python 离线环境安装。

- 首轮：12800.910 秒（3 小时 33 分 20.910 秒），2412 个上下文均尝试；806 个干净解析、1470 个部分解析，136 个因参数适配器不接受 `-w` 而在调用前端前失败。
- 修复 `-w` 后，仅补跑这 136 个上下文，约 159 秒。补跑结果为 12 个干净解析、124 个部分解析、0 个失败。这个阶段的时长来自观察到的阶段边界，保留约 1 秒精度，不冒充完整首轮计时器精度。
- 第一次合并耗时约 143.979 秒后，因 13 个析构函数的上下文类型差异被严格检查阻止。已保留输入，修复后直接重用结果。
- 成功的再次合并与导出：655.438 秒（0 小时 10 分 55.438 秒），未重跑编译前端。
- 分阶段执行时间合计约 13759.327 秒（3 小时 49 分 19.327 秒）；这是含上述修复的执行累计，不能宣称为修复版一次冷启动的耗时。人工排查间隔、后续审计压缩、网络复制及 Windows 校验另计。

源码冻结后没有编辑产品代码以绕开编译错误。原始首轮与补跑分开保留；最终 assembled run 汇总同一源码快照、相同编译 profile 的两批事实，失败上下文只允许由同输入的有效结果替换。13 个同位置类型观察保留所属上下文，`type=None` 且 `type_resolution=context_dependent`；同 TU 内的类型矛盾或证据不一致仍拒绝合并。旧首轮内部只保存了每个符号的聚合类型，本次修复不会恢复先前已经被聚合覆盖的全部类型观察。

## 为什么索引较大、产图仍较慢

首轮最后阶段，Linux `/proc/<producer-pid>/io` 采样到 `write_bytes=1,065,565,847,552`，是累计写入计数的下界观察，不是交付件大小，也不是对存储设备写入量的独立测量。首轮逐 TU 耗时记录合计 6487.834 秒，整个命令却耗时 12800.910 秒。并发任务有重叠，不能直接相减得到开销。

源码检查确认当前 `_persist_payload` 每见一个 TU 都可能更新共享头文件符号的整段 contexts JSON，CALLS 行重复保存上下文、位置及证据字段，SQLite 多个索引和 WAL 又增加写入。当前实现存在明显写放大和串行入库开销；本次没有完成存储结构和写入管线优化，增加 jobs 不能保证线性提速。

最终关系 JSON 正文字节合计 1,859,843,947，每条均值约 932.4 字节；symbols 内 contexts JSON 合计 619,442,560 字节，最多一个符号汇集 2,326 个上下文。导出图中 TU 缓存表 0 行，学习任务表 0 行，不能把这份交付图的体积归因于学习任务或 TU 缓存。

## 质量边界

最终状态仍是 `partial`，不是全仓干净语义解析。覆盖全部编译上下文不等于所有调用均正确、所有条件分支均覆盖。编译数据库只描述当前构建宏配置，其他宏组合不在本次范围内。

首轮首条错误分类中，1289 个 TU 出现 GCC 可接受而 Clang 拒绝的 const 字符串转换，145 个 TU 首报 `MB_LEN_MAX` 检查失败；另有 GNU 扩展、PATH_MAX 及缺少作为 include 使用的 `.map`、`.ini` 文件等问题。`--allow-partial` 是本次显式选择；没有隐藏诊断或把部分解析统计为成功。resolved 表示静态绑定结果，来自 partial TU 的记录仍可能不完整。

本次只使用公开 openGauss 源码，不包含商业 GaussDB；没有运行数据库 SQL 来验证运行语义。ECS 源码目录无可核实的 Git HEAD，绑定依据为冻结文件摘要、编译数据库摘要和 run。C/C++ 及头文件共 4,762 个、物理行（含空行注释）3,610,999 行。设计与用户手册未加入本次，增加文档后的任务数量需另测。

## 重现参数

Linux x86_64，16 个逻辑 CPU，约 30.3 GiB RAM，Python 3.9.9 / SQLite 3.37.2 / libclang 18.1.1，产品 GCC 10.3。分析 jobs=8，单 TU 超时=300 秒，默认 calls 模式；首次前端分析缓存为空。

~~~bash
sh ecs.sh build --source /srv/openGauss-server \
  --compile-db /srv/openGauss-server/compile_commands.json \
  --cc /srv/gcc/bin/gcc --cxx /srv/gcc/bin/g++ \
  --work /srv/kb-work --output /srv/kb-handoff \
  --jobs 8 --timeout 300 --allow-partial
~~~

GCC 路径和运行库环境必须按实际构建配置设置。不要将上述示例路径直接当作可运行路径。Windows 配置匹配源码和导出目录后执行 `kb.cmd check`、`kb.cmd start`、`kb.cmd modules`、`kb.cmd features --limit 3` 与 `navigate`。
