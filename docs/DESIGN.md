# GaussDB 源码知识工程设计 2.0

## 使用目标与部署边界

给定一个源码版本、一种构建配置和可选的设计文档、手册，团队要能回答三个问题：有哪些模块和待核实的特性，下一项由谁学，修改某项行为要同时核对哪些消费者及测试。公司 ECS 的并发 C++ 分析是上游。协调端和成员服务器使用 64 位 CPython 3.12、SQLite、Git、本地 Claude Code；NetworkX 和 pypdf 通过固定哈希的离线 wheel 安装。

~~~text
ECS                                     Windows 协调端
C++、原工具链、compile_commands.json      完整源码检出 + 设计 + 手册
            │                                       │
            └── 已完成的工程 SQLite + run_id ──────┤
                                                    ▼
                                    核验并冻结材料，按版本只读挂图
                                                    │
                                    全仓模块清单 + 图覆盖 + 特性候选
                                          │                    │
                                   模块包 A / 成员 A      模块包 B / 成员 B
                                          └────── 待审结果 ────┘
                                                    │
                                      校验版本、逐条核证、审阅提案
                                                    ▼
                                   学习 SQLite + blobs + 已审知识修订
                                          ├── Wiki / 原文和行号
                                          └── 开发 / 测试 / 评审 / 运维上下文
~~~

上游负责选哪些 TU 并发分析、宏如何取值及调用边如何解析。生产接口为单文件一致性备份，含 `runs`、`snapshots`、`symbols`、`relations`、`anchors`、`documents` 以及必要查询索引。接受 `ready` 和有摘要的 `partial` run；结果保留实际覆盖。自定义边表需先在上游适配。`check` 检查合同，`start` 继续核对快照、构建摘要和材料。缺表、多个 run 未选择或同名源码内容冲突都会返回可定位的错误。`graph_storage=reference` 是路径入口的默认值。协调端需要持续访问同一份上游文件，成员只使用自己的模块包。

## 材料身份与覆盖

Code Comprehensor 将静态 CodeGraph、分层文档 CodeScribe 和文码检索 CodeContrast 组合。这里借鉴其“从代码邻域解释行为，再按问题检索文码上下文”的分工。实现复用公司 ECS 的现有分析器和 SQLite 图，通过 MCP 提供证据与知识检索；2.0 的离线依赖中不含作者的 CodeScribe 或 CodeContrast 模型。[论文的系统设计](https://arxiv.org/html/2610.30016v2#S3)

1. 按配置遍历主仓与附加仓。保留排除项、失败原因和 SHA-256，源码与文档原文存入内容寻址的 `blobs`。Markdown、文本、HTML、DOCX、有文本层的 PDF 支持抽取；抽取失败保留缺口。CHM 应先转成 HTML 目录。
2. 用“仓库 ID＋仓内相对路径”将完整检出与上游快照清单做并集。两边都有的冻结文件以 ECS 哈希校验本地内容；只有经 LF/CRLF 还原后哈希全等才采用还原版本。新快照即使能命中旧缓存也校验当前检出。检出缺失但 ECS 有记录的资产仅在能够从同摘要 blob 恢复时使用。两侧可取得 Git HEAD 时要求相同。图外文件由本地快照绑定，未证明的构建行为保留为未知。
3. 每模块分别记录检出资产数、与上游清单重叠数、检出独有数、ECS 独有数、编译命令项数及逐 TU 实测状态。头文件、文档和测试脚本本就未必有独立 TU。没有逐 TU 回执时显示“无回执”；具体边仍以所选 run 的符号和关系为准。
4. 材料、profile 或知识修订变化各自有独立身份。同一次 `start` 复用已冻结快照，输入换版后显式 `start --refresh`。封存的交付件发生更换时保留旧工作区，新的图使用独立工作区或同时含旧 run 且绑定一致的受支持交付件。历史成果按原快照读取。

## 模块、特性、共享机制

责任树分领域、子系统、模块、机制或接口四级。特性树分能力域、功能族、特性、可独立检验的行为四级。引擎沿用 `responsibility` 和 `feature` 的层级与父节点校验。源码目录用于初始分工，可用 `module_prefixes` 细化。组织责任和产品语义归类由负责人审阅。

候选清单从冻结材料产生。规则可在 `scripts/unified_knowledge/catalog.py` 核对：

| 信号 | 候选身份和证据 | 解释边界 |
|---|---|---|
| 设计、手册章节 | 规范化标题与模块范围；常见或未匹配标题保留材料上下文 | 仅匹配标题、路径、领域别名和明确标识符。未归属项由协调人确认 |
| 内核 GUC 注册、扩展 DefineCustom…Variable | 按仓库及参数标识归并，记录注册文件与行号 | 入口支持核对默认值、赋值钩子及读取者。真实产品含义需要读实现 |
| SQL 文法 | 捕获文法文件中的具名 Stmt 产生式及行号 | 产生式是行为入口线索；一个用户特性可能包含多个产生式 |
| 回归 SQL | 一个测试脚本作为一个待核行为线索，附源码路径 | 测试名及脚本不能证明行为与运行结果 |
| 仅有手工发现的行为 | `learn --module … --question …` 直接建立研究单 | 注册表和特定目录规则遗漏的特性由成员盘点补充 |

文档点名唯一已发现的注册项时合并证据，同时记录材料关联的模块。多个同名、跨模块和泛标题保留独立线索。候选 ID 基于信号和归并键，可在键不变的快照间复用。源码证据、实际工作单及审阅状态分别绑定快照；候选 ID 的复用不继承上一版的批准状态。`route` 保存人工主责及相关模块，同计划重新盘点时继续采用。状态查询从实际任务和已接受提案生成，避免维护第二套状态机。

例如规划阶段的 `limit_tuples` 参与排序代价估算，执行阶段还要追 Limit 怎样把运行时上界传给 Sort、哪些计划节点会阻断传播。研究者应分别记录生产者、消费者、适用条件和反例，通过 `contract` 串起跨模块关系。分配器、内存上下文、错误清理等共有行为保存成 `mechanism`，各特性以 ID 引用。只有设计意图时记录设计依据；只有源码时保留原设计动机未知。

## 入队、多人协作与审阅

`PLAN.md` 先给出模块、覆盖、推荐起点及一页候选，`plan.json` 包含完整冻结清单。`features` 实时分页展示候选与状态。每模块有盘点单；产生候选本身不会创建特性任务。`learn --candidate` 或成员 MCP `focus_module` 显式建单。任务携带候选 ID、模块、证据范围、版本及研究问题。相同计划内重复请求在写事务中复用工作单；改动源码或构建后按新快照核对。找不到编译图中的符号时可在该模块文本定位，并把结果标成源码线索。

协调人按模块签发工作单。模块包包含本模块、图的一跳邻居、已分配候选引用的材料和冻结证据。研究者在独立 SQLite 中领取租约，读取实际行范围，分步保存研究单元并提交。一份工作单接收一个最终结果包，后续批次重新派单。新确认的候选归属在重发模块包后对成员生效。

收件时核验工作单、来源 run、材料摘要、源码锚点、目标符号、主责和知识冲突。同一结果的重复投递返回既有回执。中央已有未领取的同特性任务时接续该任务；在办或已审成果发生冲突时保留原记录。`review` 先审研究和反例，再按提案摘要审知识对象。只有两步都通过才在候选清单显示 `published`。`module_survey`、候选数、已解析 TU 数、已审特性数须分别统计。

## 查询、增量和未解决问题

`ask` 和 `wiki` 共用当前已审知识修订。开发查询变更前提、生产者与消费者；测试查询边界、反例与预期来源；评审查询契约、清理、重扫或并发风险；运维可读取行为和可区分场景的观测。每个结论保留源码或资料锚点、构建条件及开放项。候选调用、静态数据流和实际运行观测保留各自的证据等级。

版本更新先重新冻结变化的材料。底层 `change` 比较显式提供的两组快照和 run，检查源码、头文件、profile 与知识引用，生成需复核的工作；不是后台定时执行。线上问题缺少充分证据时，走同一模块的补学与审阅。企业私有注册宏、间接分派、未启用宏分支及缺测试的历史实现仍需人工补充。全量指可对账的源码、材料、候选和缺口；研究覆盖按已审范围报告。

## 验收条件

- 完整源码配局部图，图外模块仍可见，图内符号及源码行可回放，Windows 的 TU 解析次数为零。
- 手册和注册同一参数可归并；有测试而无设计可派单；默认特性任务数为零，重复选同一候选复用任务。
- 两个成员在隔离工作区按候选学习，中央能收件、去重、审阅、导出 Wiki，并回读三种工程角色的同版知识。
- 首次从 Git 检出或离线 ZIP 安装均走同一入口。上传范围按源码仓跟踪清单审计，实际学习库、上游图、运行日志和本机凭据由用户保管。

实际计数和验证范围见[验证记录](VALIDATION.md)。
